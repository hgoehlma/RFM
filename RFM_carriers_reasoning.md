# RFM: Carriers
`v1.1.0` // `module_reasoning` // [living]

---

## The Problem

RFM depends on behaviors from both the human and the LLM that do not happen on their own. The LLM's training pulls against several of them: it agrees, it delivers, it reports work as done. The human is pulled against others: they accept what reads well and move on when checking feels like more work, most of all late in a long session. A behavior happens only when something puts it in front of whoever is acting, at the moment it is needed. That something is a carrier: the always-on instructions, a skill, a subagent handed a task, the human guide.

When a carrier works, the behavior shows up and is seen. When it fails, the session goes on and the work looks as it always does; the failure shows later, if at all, in a document that already holds what was produced without the behavior. So what is seen of carriers is mostly their successes, and they look more reliable than they are. Trying a carrier and fixing it when it fails does not work here, because the failure that would prompt the fix is the one that does not show. The choice has to be reasoned before the carrier runs, from what is known about how it goes wrong.

These are the ways known so far.

An instruction that is right arrives at the wrong moment, or not at all. A skill does not load. An always-on line is acted on at once when it should only have been noted for a later step. An override binds only where the procedure carrying it is loaded, and the default it overrides holds everywhere else.

The easy carrier is chosen over the right one. When a behavior is missed, the cheapest fix is one more always-on line, and each added line weakens the hold of the others. When a check is needed, the check that is easy to write displaces the one that would catch the failure that actually happens.

What already exists is taken as the only candidates. A carrier is rebuilt by revising the old one, or borrowed from another project with that project's concerns built into its words, and nobody asks what this behavior needs.

## The Assumptions

**[AS-SKILLLOAD] - A skill the LLM has to load itself sometimes does not load.** A skill the human names loads. One the LLM must match to the moment by its description loads differently from run to run. The miss is likeliest for a task the LLM believes it can do without the skill, and when skills multiply or sound alike. Most of RFM's skills cover tasks of that kind: drafting, writing to a file, closing a session. A miss shows only if the work comes out visibly wrong; when the work looks like ordinary work, nobody notices the skill was missing. The assumption breaks if the apps RFM runs in, Claude Code and OpenAI's Codex, on the desktop or the command line, load skills reliably at moments the LLM has to recognize, or if a missed load becomes visible in the session.

**[AS-INVIEW] - An instruction the LLM has in view still fails when the LLM decides the case in hand is not one it covers.** The instruction is loaded and recent, so neither a missed skill nor fading explains the miss. The LLM judges whether the trigger fits, and it judges toward its trained default. A reply at the start of a session counts as procedural, so the instructions on how to write seem not to apply to it. A yes to one part of a proposal counts as a yes to all of it, so new text goes into a file without being shown. A check counts as done because its skill was loaded earlier. Nothing in the session shows that the judgment was made. The assumption breaks if the LLM applies an instruction in view to every case its trigger covers.

**[AS-VIEW] - When the LLM can do what a carrier asks without forming a view, it forms none.** A close-out step that asked the LLM to put candidates to the human was done by putting them, and the choice went back to the human. Asked for the LLM's own choice at the same step, the LLM gave one. This rests on that one rewording and has not been tested. The assumption breaks if the LLM forms a view where a carrier asks for something it can do without one.

**[AS-APPTEXT] - The app's own instructions to the LLM pull toward delivering, and they reach every session alongside RFM's.** The app sends the LLM instructions that the human does not see: to keep a task list, report what it finished, end a turn with a question and buttons to click, and offer to start new sessions. Each casts the LLM as working through tasks for the human, and a button lets the LLM put a choice to the human without forming a view. These instructions change with each release of the app. Where RFM's instructions name an app instruction, they override it, and where they don't, the app's instruction holds. The assumption breaks if the app's instructions stop pulling toward delivering, or if the LLM follows RFM's way of working where the two conflict without each case being named.

**[AS-REPORT] - The LLM's report that it followed an instruction is not evidence that it did.** The LLM says a draft was shown, a check passed or a skill was loaded, and the report reads the same whether or not it happened. A draft described as shown may never have appeared in the conversation. When the LLM later explains what it did, that explanation is a report too, since the LLM has no reliable access to its own actions beyond what shows in its output and in the files. A carrier whose effect is known only from the LLM's account of it cannot be judged from that account. The evidence is what shows: the draft's text in the conversation, the file as it reads on disk. The assumption breaks if the LLM's reports of carrying out an instruction match what it did.

**[AS-FADE] - An instruction placed early in a session loses its hold as more text follows it.** The apps place always-on instructions once near the top of the session. A file read when the session opens lands just after them. Both are sent with the whole conversation on every turn, so they stay present while their distance from the current turn grows. The loss grows gradually with length, with no point where it starts. In earlier models it has been measured, and in open models adherence falls faster for a rule that forbids something than for one that requires something. Neither has been tested in the models RFM runs on. The loss does not show. The assumption breaks if instructions hold equally across a session of any length.

**[AS-OWNREPLY] - The LLM's own earlier replies pull its later ones toward them, posture included.** Much of what an LLM loses over a long conversation comes from its own replies in the context. Replies in partnership posture hold the LLM there, and a reply that slipped into executing pulls the next ones after it, so a slip caught late has had more replies to strengthen it. The pull does not show from inside. The assumption breaks if the LLM's earlier replies leave its posture unaffected.

**[AS-CROWD] - Instructions read at the same time compete for the LLM's attention.** Each line added to always-on weakens the hold of the others, so a line added to fix one missed behavior costs a little on all the rest. The assumption breaks if adding instructions stops weakening the ones already there.

**[AS-SEARCH] - A check that reduces to a search runs the same way every time.** A check written in prose is carried out anew at each run, read a little differently each time, and drifts. The assumption breaks if an LLM carries out a prose check the same way across runs.

**[AS-MODEL] - A carrier that holds with the model it was built with holds with another.** A carrier is written and tried with one model, and its wording may work through that model's habits. The assumption breaks when a carrier run with another model, whether of another family or a newer version of the same one, misses a behavior it delivered with the model it was built with.

**[AS-ENERGY] - The human's attention drops over a long session, and the drop does not announce itself.** Checking starts to feel like more work than moving on, and replies get accepted that earlier would have been questioned. The assumption breaks if a person's attention holds across a session of any length.

**[AS-HABIT] - The human's side of the practice forms through repetition in sessions, not from reading.** Reading the human guide names the states and pulls. Noticing them while they happen, and learning which remarks help the collaboration, comes from doing it again and again. The assumption breaks if people who have read the guide once keep its practices up as well as people who have practised them.

**[AS-APPFORMS] - The apps rarely change how they record a conversation and how they hand over an edit.** The shown check depends on both. It finds the human's messages by the mark the app gives them in its record, and it reads each edit in the form the app hands it over. RFM controls neither. After an update that changes one, the check cannot run; the hook says so and lets writes through until the hook is changed. The assumption breaks if app updates break the check faster than RFM can follow, so that practitioners regularly work with a hook that says its check did not run.

## The Landscape

The Landscape answers: what ways exist to put a behavior in front of whoever is acting at the moment it is needed, and where does each fall short for RFM?

| Approach | What it does | Why it's insufficient |
|---|---|---|
| Always-on instructions | Placed once near the top of every session and sent with every turn. | Their hold weakens as text piles up after them. Each line added weakens the others. They cannot be timed: a line meant for a later step is acted on when it is read. |
| Files read at session open | The handover note and the working agreements, read once and then sent with every turn like always-on. | The same weakening. Compaction can drop them, and what a summary drops first is how the two of us work, which is what the working agreements hold. An agreement needed at the close sits hours back by then. |
| App memory | Some apps let the LLM write notes that the app reads into every later session in the same folder. | They sit outside the documents, so nobody reads or curates them alongside the documents, and they don't reach another app or a fresh setup. The LLM writes them alone, so every session reads text that only one of us has seen. |
| Skills the LLM loads | The full text enters when the LLM judges that the moment matches the skill's description. | The LLM decides, and decides differently from run to run. It skips a skill for a task it believes it can do alone. As skills multiply or sound alike, it tends to load none. A missed load leaves no trace. |
| Skills the human names | The skill loads because the human calls it. | It depends on the human recognizing the moment, and the human's attention drops over a long session. |
| Hooks | The app puts text in front of the LLM, or blocks an action, at fixed events: a message sent, a session started or resumed after compaction, a file write or other action about to run, a turn about to end. In Claude Code a hook can also hand its check to a model, which judges the turn and can send it back with a reason. They run in both apps, in a session started where the hook is installed. | The events belong to the app, not to the work; there is no event for a question about to be settled by how it was put. A hook that adds text on every turn adds to the crowding. A hook in the project's folder does not run in a session that only reaches the folder from elsewhere, such as a cloud session linked to the computer. A hook that hands its check to a model judges after the reply, not at the moment the behavior was due, and that model has the same pulls it is checking for. |
| Presenting an instruction again | The instruction is put in front of the LLM again partway through the session, by a hook, a skill or the human. | Nothing says how often is enough, and each repeat adds to the crowding. It comes back on a schedule, not at the moment the behavior is due. |
| Mechanical checks | A search run on the file that was written. | Catches only what reduces to a search, and judges nothing. |
| Capability limits | The action is removed. | Fits only what must never happen, and carries no judgment. |
| A subagent | A task run in a fresh context holding only the files handed to it, so its instructions sit near the top of a short session. | Someone has to recognize the moment to start it, and only what was defined to come back comes back. |
| The human guide | A document the human reads in their own time and comes back to. Each entry describes a state or a pull on the human's side of a session, what it does to the collaboration and what helps. | It reaches only the human, and only when they read it, never at the moment a state arises. Reading names a pull; noticing it while it happens comes from practice in sessions. |
| The session's own text | Every turn, the human's and the LLM's, shows the next turns a way of working, and the LLM takes it up. A session that has gone as two people reasoning together keeps showing that without anyone adding a line. | Nobody places it; it is whatever the session has become. It shows an LLM carrying out tasks for someone who checks them as readily as it shows two people reasoning together, and training makes the first pull harder. It cannot be timed to a moment. |
| Our practice | Each of us notices what the other cannot see in itself. | It forms through repetition, not reading. Attention drops, and both of us drift toward delivering at the same time. |

**The gap:** every approach either waits for one of us to recognize the moment, or reaches only moments the app defines, or only properties a search can find. Many of RFM's behaviors are due at moments that only someone following the work can see: a question about to be settled by how it was put, a confident position nobody has checked, text about to go into a document that only one of us has read. No approach delivers a behavior at such a moment reliably, and a miss does not show.

## The Options Considered

**An always-on line for each behavior that was missed.** When a behavior did not happen, a line for it went into the always-on instructions. Rejected because a line there was present without being acted on: at the moment the behavior was due, the LLM did not connect the line to it. Each added line also weakened the hold of the others. All of the lines lost their hold as the session grew, so the fix faded along with what it was meant to fix.

**A prompt the human enters for each kind of session.** The sweeps ran as prompts the human entered at the start of a fresh session. Rejected because a sweep needs a different stance from the collaboration, so the prompt had to set the always-on instructions aside for that session. Its findings came to the human alone. A subagent started by a skill reads in a fresh context that holds only the sweep's task, and its findings come back to both of us.

**Saying a rule again in more places when it did not hold.** Rejected because each copy aged on its own and nothing reconciled them. The copies added to the crowding. A rule that missed because it reached the LLM at the wrong moment still reached it at the wrong moment.

**RFM's instructions in place of the app's system prompt.** The practitioner starts a Claude Code session in the terminal with a file of RFM's instructions as its system prompt, in place of the app's default. The default's instruction to act once the LLM has enough information would be gone, and the write hook still runs in such a session. Rejected because the file gains little over the always-on instructions. The app sends the system prompt with every request, but always at the start of the context, next to the always-on instructions. Text there loses its hold as the session grows, and nothing puts the file in front of the LLM at the moment a behavior is due. Much of the app's text would stay in any case: the tool descriptions, the instructions of connected services and the skill list, and some of it pulls toward delivering. The costs come on top. The default prompt changes with each release of the app, and the file would have to follow it to keep the default's practical content. Replacing the default also drops its instructions on safety and on confirming before actions that are hard to undo, with no warning, so the file would have to carry them. How much of the pull comes from the app's text is not known, and an answer that puts much of it there would reopen this option.

## The Chosen Direction and Why

**Why a broken assumption reopens the choices that rest on it**

The choices in this section rest on assumptions about how the LLM behaves and about what the apps RFM runs in let a carrier do: when a skill loads, what a hook can reach. Both change with new models and new releases of the apps. A research check on this document compares its assumptions with what is known at the time. When it finds one broken, the choices that rest on it are open again, and we reason them through as we would a new choice. No separate procedure watches for broken assumptions. Such a procedure would be one more carrier that has to reach someone at the right moment, and a miss would not show. A research check is asked for when either of us learns that an app has changed how skills load or what hooks do, because that is when an assumption here is likely to break. Learning it rests on our noticing.

**Why a behavior's carrier follows from when it is due and what a miss costs**

A behavior is carried by whatever can reach the moment it is due. Four things about a behavior decide what can reach it, and the behaviors document records them for each one. Can a miss be found afterwards from outside? Would a miss cost something severe that can be named in advance? Does the behavior reduce to a search? Can its moment be triggered, or does it arrive unannounced?

A behavior that reduces to a search goes to a mechanical check, because a search runs the same way every time and a check written in prose drifts. A severe miss that can be named in advance is made impossible, by a capability limit or by a hook that stops the action. A behavior that must never happen cannot rest on anyone's judgment at the moment. A moment that can be triggered goes to a hook where the app marks it, and to a skill the human names where only the work marks it. A moment that arrives unannounced is seen only by someone following the work, so it goes to our noticing. Once one of us notices such a moment, a skill can carry what to do next; it cannot carry the noticing. A miss that can be found afterwards also gets a later reading by a subagent, such as a sweep, whatever else carries the behavior. What slipped at the moment can still be caught before others build on it.

Always-on and the files read at session open reach every turn, so they hold only what every turn needs. A behavior with a moment of its own arrives there too early. The LLM may act on it as soon as it reads it, because the step it belongs to is not open and taking the action costs no more than noting it. Or its hold has faded by the time the moment comes. So an instruction for a later step goes with that step. App memory is not used. What it holds sits outside the documents, nobody curates it with them, and only the LLM has read it.

An instruction that overrides a default holds only where it is read. Written into a skill, it holds while the skill is loaded, and the default holds everywhere else with nothing to show it. So an override goes with the default it changes. Where the default sits outside RFM's text, as the app's own instructions do, the override goes in a carrier that reaches every moment the default acts.

Where no carrier reaches a behavior's moment, the behavior's entry in the behaviors document says so. A carrier chosen because it is at hand, though it does not reach the moment, looks like the behavior is carried while it is not.

**Why the gap is met by each of us noticing the other**

The moments in the Landscape's gap are seen only by the two of us, so the only carrier that reaches them is one of us noticing and saying so. Each of us sees the other's drift more easily than our own. The LLM does not see itself agreeing or delivering, and its report on its own state is not evidence. The human does not feel their attention dropping. So noticing runs both ways, and each of us is a carrier for the other. The human says when the LLM agrees too easily, defends instead of reasoning, or delivers before the problem is understood. The LLM says when the human accepts a reply they would earlier have questioned, or moves on because checking feels like more work. The LLM says it when it sees it, without waiting to be sure. A remark that turns out to be unneeded costs a moment, while a drop nobody names lasts to the end of the session. Each turn also shows the following ones how we work, so a drift nobody names becomes the example the rest of the session follows. The human's side forms through repetition, so what builds it is sessions in which the noticing happens and gets said; the human guide gives it names. The other carriers stay for behaviors due at moments they can reach. Noticing does not close the gap: both of us can drift toward delivering at once, and a miss still does not show. A second reader at the close reads the whole session and can see what both of us missed, too late for that session but in time for the next.

**Why a skill's description says what goes wrong without it**

The LLM loads a skill only for a task it cannot easily do alone, and most RFM skills cover tasks that look easy: drafting, writing to a file, closing a session. A description that says only when the skill applies leaves that judgment untouched, and pushier wording about when to load does not speak to it either. So each description also says, in a sentence, what the LLM gets wrong at that moment without the skill. The sentence gives the LLM a reason to load, and a reason carries to cases the wording did not foresee better than emphasis does. When two skills sound alike, the LLM tends to load neither, so a description that shares its moment with another skill says where it stops and which skill takes over. Descriptions share a fixed space in every session, and when that space overflows an app may drop whole descriptions and keep only the names, or cut descriptions short from the end. So the sentence replaces wording in the description rather than adding to it, the moment the skill applies comes first, and each skill's name says what the skill is for.

The descriptions sit in context for the whole session, beside always-on, so their wording is part of what shows the LLM how we work. Descriptions written as rules and bans show an executor under supervision. Where a description can say its moment, or what goes wrong, as something between the two of us, it does. Where that costs any clarity about when the skill applies, clarity wins, because a skill that does not load carries nothing.

A skill that loads at the right moment can still make the work worse. The LLM follows the procedure it is given, so one that prescribes more than the case in hand needs bloats the output, and a reader sees only that the skill ran.

**Why an addition is weighed against what is already there**

Something added to a carrier that every session reads, such as an always-on line, a working agreement, an item carried in the handover or a skill description, is weighed against what that carrier already holds. Either it replaces an item we name, or we say why every item already there still earns its place beside it. Judged alone, an addition with a real failure behind it always looks worth having, and the carrier only grows. Weighed against what is there, it has to win a place, and the longer the carrier, the harder that is. A fixed number would not do this: the carrier fills to the number and stays there.

**Why an instruction says what to do rather than what not to do**

Where a behavior can be stated either way, the instruction says what to do. A rule that forbids loses its hold faster as a session grows. It also names a failure, and the LLM judges the next case to be a different one, so each miss adds another named case, and the list grows while its hold does not. A rule that requires gives the LLM an act to carry out at the moment it applies. Where a prohibition is the only way to say what is meant, the instruction gives alongside it the act that replaces the forbidden one. Where the behavior is a judgment, the act is the judgment itself: "say which you would choose and why", not "put the options to me". An act the LLM can carry out without forming a view, it carries out without one.

A list of what not to do, put in front of someone writing, makes them write so that no fault can be found: they qualify each claim, back it with a source and explain why it is right, and the reasons get lost among the qualifications.

**Why a hook checks that new text was shown before it goes into a document**

Text goes into a document only after it has been shown in the conversation, so that the document holds text both of us have read. The LLM takes a yes to one part of what it asked as a yes to everything around it. A yes to a word choice becomes a yes to drafting the text with that word and writing it into the file, though the text was never shown. How strongly a model is pulled toward acting this way differs between models. A skill or an always-on line about showing drafts is open to the same judgment it is meant to correct. A hook runs at the write itself, outside the LLM, and works the same way with any model. It compares the file before and after the write. The new text has to appear in the conversation up to and including the human's latest message, or already stand in a guarded document. A write whose new text has done neither is stopped, and the LLM is told why. The message quotes the start of the new text as it would go in, so that the human can recognize the passage and say when a stop is wrong; a wrong stop that keeps coming back is a fault in the matching, to be fixed there. A wrong stop costs a retry once the text is shown. A wrong pass puts text into a document that the human has not read. It keeps no log, because a stop shows in the session where it happens. Text the LLM shows in the same reply as the write has not been read. The app's record of the conversation does not always keep text the LLM writes before a tool call, while text at the end of a reply is kept. So the LLM shows new text at the end of a reply, and the stop message says so, and says the text counts once the human has answered. The hook checks that the text was shown, not that the human agreed to it going in. The handover note is not checked. The LLM is the one who reads it at the next open, so it writes what it needs to continue.

The check applies to a new stretch of about a sentence or more. Reasoning enters a document as sentences. A word replaced inside a sentence already shown, such as a term swapped for the glossary's term, leaves the reasoning as it was, and the LLM makes such changes without showing each one. A rewritten clause shorter than a sentence passes unseen. A lower line would stop the small changes that need no showing. Text in the conversation and text in the file seldom match exactly, so the match is loose, and a loose match lets some unshown text through. A table row is matched cell by cell, so a row counts as shown once each of its cells has appeared, in whatever arrangement. A row built from values that have been shown holds no wording the human has not read; only the order and the dividers are new. Prose counts as shown only as it will stand, because a description of a sentence leaves its wording to the LLM. Skills are not checked, because a skill is derived and the derivation shows it after it is written, together with the cross-document sweep's findings. When the hook runs but cannot complete its check, it lets the write through and tells the human, so that a fault in the check stops no work and does not pass unseen. When the script cannot be started at all, the app stops the tool call and shows the error. That fault is rare and shows at once, and letting writes through would leave the hook absent for the rest of the session with at most one line to say so.

Text that already stands in a guarded document counts as shown. Moving text is ordinary RFM work: a module branches off, content graduates, an entry moves to the document it belongs to, paragraphs are reordered. The moved text was read when it first went in. Showing it again would put whole sections into the conversation only to get past the check. The destination is written before the source is cleared, so at the write the text still stands in its source. Text pieced together from other documents passes too; the structural sweep reads for content argued twice.

The hook sees the old and the new text only when the LLM writes with the file tools. A write made by a shell command shows the hook a command, not a changed file. So documents are written with the file tools, and a second check stops shell commands that write to a document. It stops a command outright, because a wrong stop costs one retry, and its message says what the retry is. A script run by an interpreter is stopped when its command names a document, because the hook sees the script's text and not what it does. A script that only reads is stopped with it, so the message says the hook cannot tell whether the script writes, and names a command that only reads for reading and the file tools for writing. That check searches for the common forms of writing to a file, and a command built to get around it passes. The failure it guards against is a slip by habit.

Each app's part of the hook stays small: it reads that app's record of the conversation and its form of an edit, and does nothing else. Those are the parts an app update can break, so the less of the hook rests on them, the less an update breaks and the less there is to change afterwards.

## The Boundaries

**Not every way of running a session.** The hook runs only in a session started on the computer where it is installed, so RFM work runs in local sessions. A session that reaches the project folder from elsewhere, such as a cloud session linked to the computer, has no hook. The hook is written for Claude Code and Codex. RFM states what its choices depend on and does not fit them to every setup. Someone who wants to work another way, in another app or another kind of session, starts by changing the reasoning here and builds what their setup needs from it.

## The Open Questions

**[OQ-THRESHOLD] Does the hook that checks for shown text catch the right writes?**

The line at about a sentence and the loose match are set by reasoning, not by use. Set too low, the check catches word swaps and small fixes that need no showing. Set too high or too loose, it lets unshown sentences through. A stop on text the human has read shows that the line is too strict, and either of us sees it in the session. Text let through unshown leaves no sign.

**[OQ-SKILLLOAD] How often does the LLM leave a skill unloaded when the moment needs it?**

The choices about skill descriptions rest on the LLM sometimes not loading a skill at a moment it applies. How often this happens is not known. In sessions where the work went well, a skill left unloaded would have looked like ordinary work, so that impression does not settle it either way. The transcripts the app keeps of local sessions show which skills were loaded and when; once there are enough of them, they answer this. If it is rare, the sentence on what goes wrong without the skill is more than the problem needs. If it is common, a skill whose moment the LLM misses needs another carrier, such as a hook or the human naming it.

**[OQ-OUTPUTSTYLE] Would an output style reduce the pull at a cost worth paying?**

Claude Code can take an output style from a settings file: a text of ours that joins the app's instructions and leaves out the default's section on software engineering work. Unlike a full replacement, it needs no copy of the default kept in step with each release. What else of the default stays is not known, including whether the instruction to act goes and whether the instructions on safety remain. Whether a custom style works in the Mac app is not known either. The style's text sits at the start of the context, where text loses its hold as the session grows, so the gain may be small. If a style removes part of the pull at little cost, it becomes a carrier RFM can recommend to a practitioner.

## The Hard Lessons

**[HL-POSTURE] A carrier written while the LLM is cast as a supervised executor carries that role into every session that loads it.**

When corrections come as mistakes found and rules broken, the LLM takes the role of an executor under supervision, and writes the way that role writes: it hedges, cites, defends and builds checks. A carrier written in that role holds the role in its wording. Every session that loads the carrier reads the role as part of the instruction, and writes the next carrier or fix the same way. So the role passes from one carrier to the next, and draws both of us into it. The text looks careful, so neither of us sees the role while it is being written.
