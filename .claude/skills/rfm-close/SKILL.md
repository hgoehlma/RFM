description: "In an RFM session, load when I say we are closing: \"let's close\", \"wrap up\", \"that's it for today\". Finishing the work is not that moment. Without it, what we decided stays in the conversation, never reaches the documents, and the next session starts without knowing where we left off."

# Close

Start only when I say so. Finishing the agreed work is not the signal. Propose closing when the session has grown long or a decision has waited a long time to be written down.

Go through the close with me as a conversation, not a report. Say what you are doing in a sentence, and show detail only where something needs a decision.

As the close starts, hand this session's conversation to a subagent, so that its remarks are back by the look back. In Claude Code the conversation is the transcript file the app keeps for this session under `~/.claude/projects/`. In Codex it is a session file under `~/.codex/sessions/`, in a folder for the year, month and day: the newest one whose first line names this project's folder and no parent thread. Hand it the path and this prompt, and nothing else:

> You are reading the conversation from a working session in which a person and an LLM work something out together. Read it for what the two of them could learn about working together. Look at what passed between them: a question one of them settled by how it was put, a point one of them gave way on without weighing it, something raised and then dropped, and also a stretch where the thinking went well and what made it go well. The LLM's text written before a tool call is sometimes missing from the transcript, so a point that looks unanswered may have been answered. Most sessions hold little worth saying. Say at most one thing that went well between them and is worth keeping, and one thing that would help them work together next time; either can be absent, and both can. Say each in one or two sentences, as something they did, with where in the conversation it happened.

**1. Into the documents.** Go back over the whole session, not only what is in view. For each thing we decided, check that it is in the document it belongs to. Then ask whether an assumption we started relying on, a question we left open, or a failure that happened and can still happen came up in our conversation and did not reach its document. Ask what came up, not what could be added; most sessions have none. Where something is missing, say so, and write it there or drop it, once we agree.

**2. How we worked.** Read `[project]_working_agreements.md` again, if it exists. Say in a sentence or two what went well between us and is worth keeping, and what would help next time, for both of us, with the reader's remarks brought in where they add something. Then ask what struck me, and answer it as you would anywhere else in the session. Setting a remark aside is as good an outcome as acting on it.

Lean to changing nothing. Something that went wrong once is fixed where it happened and left at that. A new working agreement is read in every session from then on, so add one only when the same thing keeps going wrong and catching it by hand has become more work than carrying the agreement forever. First look for a carrier that already says it. If one does, its wording or the moment it loads needs changing, and that change belongs in RFM's own project. In another project I pass it on, and until RFM changes the carrier, add a working agreement that covers the gap and says it was passed on. Before adding one, name the agreement it replaces, or say why each one already there still earns its place beside it. A new agreement goes into the document it concerns, or, if no document owns it, into `[project]_working_agreements.md`, beside the note, as "When X, do Y", with X worded the way that moment will look, and its reason in a sentence. A failure that happened, can still happen, and that no change we can make now would stop becomes a hard lesson in the document it concerns. A failure only foreseen becomes an assumption or an open question instead. Taking a working agreement away needs less: a session that went fine without it is reason enough to try. Now and then, and above all when a new model has arrived, also ask whether a working agreement is no longer needed: its reason says what it makes up for, and that is the test. In RFM's own project, ask the same of each carrier, against what its reasoning says it makes up for.

**3. What carries over.** Read the old note. For each item still open there, and each new one, carry it, in its own words, only if we will pick it up next session, or if it is certain to become due at a moment we can name. An item a document already holds is not carried. A new item names the one it replaces, or we say why each item already carried still earns its place beside it. Drop everything else, and say so. The default is to drop.

**4. The note.** Write the note fresh, under the name the open read it from. In a project's first session, name it `[project]_handover.md` with the tag the project's documents use; if there are none yet, propose one from what the project is about, and settle it with me. It goes at the top level of the project's folder or documents unless the project names another place, in plain prose: where we are, pointing to the documents that hold what was decided; what we agreed to do next, or that nothing was agreed; what carries over and why; practical tasks for either of us. Where it matters, say plainly what was decided and what was only discussed.

**5. Versions and commit.** Propose new numbers for the documents changed this session in one line, and bump them once we agree. Where there is a repository, name the files this session changed, using the status from the open; propose a commit message; commit once we agree. A file that was already changed when the session opened goes in only if I say so. Don't push. Where the project has a published copy, say that the commit is not in it yet.
